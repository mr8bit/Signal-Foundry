# Фоновый сбор с паузами

В production `collector.py` использует `SourceSchedule`: за одно задание обновляется один готовый источник. Обхода всех лент каждые 15 минут больше нет. Остальные записи сохраняются в снимке; дашборд продолжает читать готовую публикацию. При ошибке источник сохраняет предыдущие записи и получает статус `stale`, если они есть. Их исходные даты не меняются.

## Интервалы

Настройки находятся в `config.json`, секция `collection`:

| Источники | Минимальный интервал после обработки |
|---|---|
| Новостные RSS, HN, HTML Anthropic | 30 минут |
| Каждая из двух Reddit-лент | 60 минут |
| GitHub Trending и HF Models | 60 минут |
| HF Papers | 120 минут |
| Блоги лабораторий, авторские рассылки, VentureBeat | 60 минут |

К интервалу добавляется случайная задержка от 0 до 15%. Индивидуальный `poll_seconds` в настройках источника переопределяет интервал. Это интервалы обновления источника; TTL HTTP-кэша остаётся отдельным ограничением.

Между заданиями действует пауза от 10 до 11,5 секунды. Один домен обслуживается последовательно с общей паузой не менее 10 секунд; для Reddit и VentureBeat — 60 секунд. Эти ограничения действуют также для полных текстов статей, которые догружаются внутри обработки источника. Во время такой догрузки остальные источники ждут. Проверки кэша не создают сетевых запросов. На новой пустой установке начало опросов разнесено примерно на первые пять минут, чтобы не отправлять весь список сразу.

Паузы на домен задаются в `cache.host_min_intervals`, общая пауза — `cache.min_host_interval_seconds`. Блокировки и HTTP-кэш общие для всех процессов, использующих эту базу.

## Ошибки и ограничения

После HTTP 429 общая пауза домена увеличивается: базовые 30 минут, затем 60, 120 и далее с ограничением локального backoff до 24 часов. Добавляется только положительная случайная задержка до 20%. У сетевых ошибок и других неуспешных ответов база — 15 минут, счётчик хранится на URL. Для 403/503 также действует пауза домена. Успешный 200/304 сбрасывает соответствующие счётчики ошибок.

Для 429 и 503 учитываются обе формы Retry-After: число секунд и HTTP-дата. Срок сервера не сокращается локальным лимитом 24 часа. Следующая попытка выполняется после всех ограничений: собственного интервала источника, URL backoff, паузы домена и общей паузы сборщика. Поэтому фактическое ожидание может быть дольше указанного Retry-After. [Семантика Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after), [статус 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).

Не выполняются смена IP, ротация User-Agent, немедленные повторные запросы или сброс backoff при перезапуске. Это снижает частоту запросов, но не гарантирует отсутствие 429: лимиты зависят от сервиса и общего трафика с IP.

## Состояние и ручное обновление

Расписание, последние успешные данные каждого источника и результаты проверок находятся в таблице `source_schedule` базы `service.sqlite3`. Общая очередь ручных заданий использует ту же базу. Сроки HTTP backoff и счётчики ошибок хранятся в `http-cache.sqlite3`. Обычная резервная копия включает обе базы.

Кнопка «Обновить» ставит задание на обработку готового источника. Если ни один ещё не готов, задание завершается с прежней публикацией, без сетевого запроса. Кнопка не ускоряет проверку всех лент и не сбрасывает ограничения. `collector.py --once` также соблюдает расписание и обрабатывает максимум один готовый источник.

Список источников показывает время следующей проверки в `next_fetch_at`; `retry_at` отражает HTTP backoff. При выборе времени учитываются также общая пауза и состояние домена. Эти сроки могут сдвинуться, если другой запрос получит новый 429 или один источник долго отвечает. `collected_at` снимка берётся из последней успешной проверки данных, а не из времени неудачной попытки. Статусы и расписание публикуются даже при частичной недоступности источников, если есть данные для ленты.

```sh
docker compose logs --tail 100 worker
docker compose exec worker python source_diagnostics.py
```

Диагностическая команда с `--probe` — отдельная ручная проверка через обычный HTTP-кэш. Она соблюдает TTL и паузы домена/URL, но не заменяет фоновое расписание и не обновляет его. Для обычного обновления используйте дашборд.

Локальные команды `bot.py` и `scripts/check_feeds.py` остаются средствами разового чтения. Их нельзя запускать параллельно с production-сборщиком на этой же базе; они используют общие HTTP-паузы, но не production-расписание.
