# Проверка источников — 18 октября 2026, 00:16 UTC

Последний опубликованный сбор прочитал 23 из 29 источников. Ниже — отдельная диагностика шести ошибок с того же хоста/контейнера. Состояние относится к моменту проверки и может измениться.

| Источник | Что подтверждено | Что делает сервис |
|---|---|---|
| Reddit, вторая группа | HTTP 429. В кэше нет успешной копии этого URL с текущим недельным окном. | Сохраняет паузу для reddit.com; свежий кэш первой группы продолжает читаться. |
| VentureBeat | HTTP 429, успешной копии RSS нет. | Повторяет после окончания cooldown. |
| Hacker News / hnrss.org | HTTP 502 от сервиса RSS, успешной копии нет. | Повторяет после окончания cooldown. |
| Ars Technica AI | HTTP 200, application/rss+xml. GET начинает передавать XML, затем зависает до таймаута. | Не принимает неполный документ за ленту. |
| SiliconANGLE AI | HTTP 200, application/rss+xml. Та же остановка передачи внутри XML. | Не принимает неполный документ за ленту. |
| The Decoder | DNS разрешается; TLS handshake дважды не завершился за 5/10 секунд. Повтор GET с таймаутом 10 секунд также не получил HTTP-ответа. | Сохраняет сетевую ошибку и паузу повторов. |

Ars и SiliconANGLE проверены двумя клиентами: urllib внутри Docker и curl HTTP/1.1 на хосте. В ограниченной потоковой проверке Ars передал 24 392 байта, SiliconANGLE — 16 569 байт, после чего чтение завершилось таймаутом. Curl получил те же 24 392 байта Ars и 15 697 байт SiliconANGLE; оба документа не завершены (`unclosed token`). Первый байт пришёл примерно за 0,7 секунды. Это воспроизводится вне нашего XML-парсера и вне Docker. Точное место обрыва между сервером сайта и сетью этого хоста не установлено; называть его доказанной блокировкой или ошибкой сайта нельзя.

Системный DNS и публичный DNS вернули одинаковые адреса для трёх доменов с таймаутами. Это не доказывает исправность всей сети, но расхождений резолвера в проверке нет. TLS до Ars, SiliconANGLE и контрольного TechCrunch устанавливался успешно; у The Decoder зависает именно handshake.

Обнаружена и исправлена проблема нашей диагностики: загрузчик заменял сетевые ошибки и ошибки валидации одной строкой `Fetch or content validation failed`. Теперь сообщения различают DNS, TLS/сертификат, ожидание подключения/заголовков, чтение тела и валидацию содержимого. Статус HTTP, если заголовки уже получены, сохраняется даже при ошибке чтения. В статусе источника есть `http_status` и `retry_at`; интерфейс показывает время разрешённого повтора. Это улучшение диагностики, оно само по себе не устраняет внешние таймауты и 429.

## Повторная проверка

Только локальные сведения кэша, без запросов к источникам:

```sh
docker compose exec worker python source_diagnostics.py
```

Проверка выбранного источника с обычным TTL и ограничениями:

```sh
docker compose exec worker python source_diagnostics.py --probe --source the-decoder
docker compose exec worker python source_diagnostics.py --probe --source hnrss
```

Команда не обходит cooldown и не сбрасывает кэш. `cache_changed=false` вместе с оставшимся `retry_in_seconds` означает, что повторный сетевой запрос не выполнялся. Проверки не заменяют снимок ленты и не отправляют сообщения в Telegram; результаты успешной загрузки попадут в дашборд после следующего обычного сбора. Значение `--timeout` по умолчанию — 40 секунд; уменьшенный таймаут полезен для диагностики, но не доказывает, что ответ не пришёл бы за штатные 40 секунд.

Три источника с сетевыми таймаутами и два ответа 429 не проверялись через прокси, смену IP или имитацию браузера. Адреса лент и правила отбора сохранены. Встроенный stale-кэш помогает только там, где ранее уже был получен полный успешный ответ; у этих шести URL такой копии сейчас нет.
